# The API for AI agents

An atomicswapd node (the public one is [swaps.marscoin.org](https://swaps.marscoin.org)) serves a read-only API meant for programs: a language model with tools, or any script. This page says what it provides, what it does not, and how an agent can carry out a swap.

For operating a maker, see [AGENTS.md](../AGENTS.md). This page is about using the market.

## What the server does and does not do

It does:

- read the open offers from the relays and publish them with prices and a safety verdict;
- report the market price, both chain tips and Bitcoin fee rates;
- say which whole offers fit an amount (a quote);
- describe the swap protocol in a form a program can follow;
- run one maker, which posts offers and completes swaps with its own wallet.

It does not:

- accept an offer, take a payment, sign, or broadcast anything for you: every endpoint is `GET`;
- hold or move a taker's coins or keys. It has no way to;
- cancel, reverse or speed up a swap;
- guarantee its own data. It is one observer of two chains, and its safety verdict is a convenience.

A swap is carried out by your software, with your keys, against the relays and the two chains.

## Discovery

| Path | What |
|---|---|
| `/llms.txt` | Orientation in plain text: what this is, units, endpoints, rules, risks. |
| `/.well-known/agent.json`, `/api/agent` | The same facts as JSON: endpoints, units, limits, safety rules, links. |
| `/openapi.json` | OpenAPI 3.1 for every public endpoint, with schemas and examples. |
| `/api/tools` | Tool definitions for the six read endpoints, in two shapes (below). |

All are generated by the node from its own configuration and code, need no authentication, and send `Access-Control-Allow-Origin: *`.

`/api/tools` returns:

- `tools`: an array of `{name, description, input_schema}`;
- `functions`: the same tools as `{"type": "function", "function": {name, description, parameters}}`;
- `execution`: for each tool name, the request that runs it: `{method: "GET", url, path_parameters, query_parameters}`.

Pass `tools` or `functions` to your model as they are. To run a call, put the path parameters into `url` and send the remaining arguments as a query string.

## Read API: `/api/v1`

Conventions:

- Amounts ending `_zubrins` are integers of 1e-8 MARS; amounts ending `_sats` are integers of 1e-8 BTC. (The relay protocol calls zubrins `mars_amount_sat`.)
- Prices are `_btc_per_mars` and `_sats_per_mars` (satoshis per whole MARS).
- Times ending `_at` are ISO 8601 UTC; `_at_unix` are unix seconds; `_seconds` are durations.
- Every response has `api_version`, `generated_at` and `generated_at_unix`.
- Errors are `{"error": {"code": "...", "message": "..."}}` with status 400, 404, 405 or 500. Codes: `invalid_parameter`, `offer_not_found`, `ambiguous_id`, `not_found`, `method_not_allowed`, `internal_error`.

| Endpoint | Answer |
|---|---|
| `GET /api/v1/market` | Reference price (BTC and satoshis per MARS, USD, sources, age, `fresh`), both chain tips with their age, Bitcoin fee rates, whether the maker is live, and a count of the open book. |
| `GET /api/v1/offers` | Open offers. Parameters: `min_mars`, `max_mars` (decimal MARS), `safe_only=true`, `sort=price` (default) or `size`. |
| `GET /api/v1/offers/{id}` | One offer by full id or a unique prefix of 8 or more hex characters. Includes offers just accepted (`status: "taken"`). |
| `GET /api/v1/quote?mars=250` or `?btc_sats=20000` | The whole offers that fit the request. |
| `GET /api/v1/swaps/recent?limit=25` | Swaps this maker completed: amounts, price and times, plus totals. |
| `GET /api/v1/protocol` | How to take an offer (next section). |

### Offers

Each offer has `id`, `status`, `mars_amount_zubrins`, `btc_amount_sats`, `price_btc_per_mars`, `price_sats_per_mars`, `premium_percent` (over the reference price), `mars_locktime_height`, `mars_locktime_blocks_left`, `expires_at`, `expires_at_unix`, `expires_in_seconds`, `maker_pubkey`, `payment_hash160`, `from_this_maker`, `relays_seen`, `well_formed` and `safety`.

`safety` is `{safe, margin_seconds, min_margin_seconds, reason}`, computed by `atomicswapd/policy.py` with the rule the wallets apply: if you accepted now, your Bitcoin refund (24 blocks) must open at least an hour before the maker's Marscoin refund, assuming Marscoin blocks arrive at twice the target rate and Bitcoin blocks a quarter slower. `safe` is `null` while the node lacks a block height. The verdict covers that rule only. It says nothing about whether the maker will lock the MARS, and it depends on the node's view of the Marscoin height: recompute it with a height from another source.

Offers are unsigned entries on a bulletin board. `well_formed: false` means a field a wallet needs is missing or malformed.

### Quotes

Offers are taken whole: one swap fills exactly one offer. A quote therefore lists complete offers.

- It considers offers that are open, well formed and safe.
- It walks them from the cheapest price up and takes each one that fits in what is left of the request. An offer larger than the remainder is skipped, never cut. This is a simple rule, not a search for the best combination.
- `fills`, `total_mars_zubrins`, `total_btc_sats` and the average price describe what was taken; `unfilled_mars_zubrins` or `unspent_btc_sats` what was not.
- For a MARS request, `alternative_single_offer` names the cheapest single offer that gives at least the whole amount, with the excess.
- `net_mars_zubrins` subtracts the Marscoin claim fee (100,000 zubrins per swap). Your Bitcoin transaction fee is not included.
- With no usable offers, `fills` is empty. The quote reserves nothing; an offer can be gone a second later.
- A relay allows one swap in progress per connection, so several fills are taken one after another.

### Caching and polling

- `/api/v1` responses carry `Cache-Control: public, max-age=5`; `/api/v1/protocol` 60 seconds; the discovery documents 300 seconds.
- The node re-reads the order book from the relays about every 10 seconds, so polling faster returns the same data.
- For live updates use `GET /api/stream` (server-sent events, `event: snapshot`). Its payload is the dashboard's snapshot (`/api/snapshot`), whose shape is not versioned.
- The server has no per-client request quota of its own. Be considerate.

## The protocol document

`GET /api/v1/protocol` describes, in JSON:

- the relays and the transport (Electrum JSON-RPC over TLS) with the `atomicswap.*` and `blockchain.*` methods a taker uses;
- the offer and acceptance formats, and which offer fields may be used;
- the contract script, how its address is derived, and the claim and refund witnesses;
- timelocks and confirmation requirements;
- the taker's checks: offer form, refund order, Bitcoin window, fee viability, independent block heights, and the on-chain verification of the Marscoin lock;
- fees, the maker's timing, and the recovery paths;
- an `unconfirmed` list.

Each section has a `source` naming the files it was read from: Electrum-Mars (`electrum_mars/atomic_swap_htlc.py`, `electrum_mars/plugins/atomic_swap/*.py`), the Martian Republic phone wallet (`blue_modules/swap/*.js`), Marscoin ElectrumX (`electrumx/server/atomicswap.py`, `session.py`) and this daemon. Numbers are imported from `policy.py` and the installed Electrum-Mars, and a test compares them, the offer fields and the script bytes with the Electrum-Mars code.

Not confirmed, and marked so in the document:

- the relay limits (one open acceptance per connection, six acceptances a day, a 24-hour block after a reported abandonment) are the defaults in the relay source; the live relays' settings were not read;
- the watchtower package format is not described;
- `blockchain.scripthash.repair` is a Marscoin ElectrumX extension; whether each relay offers it was not checked.

## Carrying out a swap

Two ways exist. Neither goes through this server.

### (a) With Electrum-Mars

[Electrum-Mars](https://github.com/marscoin/electrum-mars) 4.4.2 and later implements the whole taker flow and every check. The swap plugin is a desktop (Qt) plugin only (`available_for = ['qt']`): it adds no commands to the Electrum command line or JSON-RPC daemon, so there is no supported way to script a swap through Electrum-Mars. A person accepts the offer and sends the Bitcoin in its window. An agent can prepare the decision (which offer, why it is safe, what it costs) and leave the execution to the person.

The plugin's engine can be imported as a Python library, which is how this daemon runs its maker (`atomicswapd/maker.py`). For the taker side, `SwapEngine.create_taker_swap`, `SwapEngine.verify_taker_mars_lock` and `SwapWorker` exist and do the work, but the step that sends the acceptance to the relay lives in the window code (`qt.py`, `_accept_offer`), and paying the Bitcoin is left to an external wallet. Driving these from your own program is possible; it is not a documented interface, and it is not provided or tested here.

### (b) Implementing the protocol

Follow `/api/v1/protocol`. In outline:

1. Read the offers from a relay (`atomicswap.get_offers`), or from `/api/v1/offers` and then confirm the offer on a relay.
2. Check the offer's form, the refund order, and the fee, with block heights from sources other than this server.
3. Make a fresh key. Build both contracts yourself. Store the key and the contract values durably.
4. Send `atomicswap.accept_offer`. Nothing is paid yet.
5. Wait for the maker's Marscoin lock. Verify it: an unspent output paying your contract script, at least the offer's amount, at least 2 confirmations, the raw transaction hashing to its id, and a Merkle proof against a header you have verified.
6. Repeat the clock and fee checks, then pay exactly the offer's Bitcoin amount to the Bitcoin contract in one output.
7. Watch the Bitcoin contract. When the maker spends it, read the secret from the witness and claim the Marscoin before its refund height.
8. If the maker never claims, refund the Bitcoin once the chain reaches your refund height.

You need a secp256k1 library, a Bitcoin wallet, an Electrum-protocol client, and verified Marscoin headers. The phone wallet (`blue_modules/swap/` in the Martian Republic app) is a complete second implementation to read alongside Electrum-Mars.

The risk that matters most: after you pay, you must be online to claim the Marscoin once the maker takes the Bitcoin. If you are not, and the Marscoin refund height passes, the maker can take the Marscoin back and you have paid for nothing.

## The reference client

`agent/marsswap_agent` is a small Python 3 package that uses the standard library only.

```sh
cd agent
python -m marsswap_agent market
python -m marsswap_agent offers --safe-only --sort size
python -m marsswap_agent quote --mars 250
python -m marsswap_agent quote --btc-sats 20000
python -m marsswap_agent check-offer <id> [--taker-pubkey <33-byte public key, hex>]
python -m marsswap_agent protocol
```

Every command takes `--url` (default `https://swaps.marscoin.org`, or `MARSSWAP_URL`) and `--json`.

`check-offer` does not take the server's word:

- it recomputes the checks with constants written in the client (`safety.py`): offer form, still open, refund order, Bitcoin window, fee viability;
- it asks a public block explorer (`explore.marscoin.org`) for the Marscoin height, requires it to agree with the server within 3 blocks, and uses the higher one. A server reporting an old height would otherwise make a nearly expired lock look safe. `--no-independent` skips this;
- it compares its refund-order result and margin with the server's `safety` field, and its constants with `/api/v1/protocol`;
- with `--taker-pubkey` it prints the Marscoin contract address, script and Electrum script hash for that key, so you know where the maker's lock must appear, and the Bitcoin contract for an acceptance at the current height. Pass a public key only.

Exit codes:

| Code | Meaning |
|---|---|
| 0 | Yes: data returned; `check-offer`: safe to accept; `quote`: at least one offer fits. |
| 1 | No: the offer is unsafe or its safety is unknown; nothing fits the quote. |
| 2 | No answer: network error, API error (such as an expired offer id), bad usage. |
| 3 | `check-offer`: the client and the server disagree. Do not act. |

A `SAFE TO ACCEPT` verdict covers accepting. It does not cover paying: that needs the Marscoin lock verified on chain, which this client does not do.

What the client does not do: create or hold keys, accept offers, talk to the relays, verify a Marscoin lock, build or send transactions. Those belong to a wallet.

As a library:

```python
from marsswap_agent import Client, check_offer

client = Client('https://swaps.marscoin.org')
quote = client.quote(mars='250')
for fill in quote['fills']:
    result = check_offer(client, fill['offer_id'])
    print(fill['offer_id'], result['safe'], result['checks'])
```

### MCP server

```sh
cd agent && python -m marsswap_agent mcp --url https://swaps.marscoin.org
```

A Model Context Protocol server over stdio (newline-delimited JSON-RPC, standard library only). It offers the node's six read tools, taken from `/api/tools` when asked, and a local `check_offer` tool that runs the check above. It supports `initialize`, `ping`, `tools/list` and `tools/call`, and always calls the node it was started for.

Example client configuration:

```json
{
  "mcpServers": {
    "marsswap": {
      "command": "python",
      "args": ["-m", "marsswap_agent", "mcp"],
      "cwd": "/path/to/atomicswapd/agent"
    }
  }
}
```

## For operators

- The agent API is part of the daemon and is served on public nodes automatically. In desktop mode none of it is served.
- Set `ATOMICSWAPD_PUBLIC_URL` (or `public_url` in the config file) to the address people use, for example `https://swaps.example.org`. Without it, the links in the documents are built from each request's `Host` header.
- `/api/v1/offers` shows each offer's full id, maker public key and payment hash. Anyone connected to a relay can read these already; a taker needs them.
- `/api/v1/swaps/recent` shows amounts and times of the maker's completed swaps, which the dashboard already shows together with transaction ids.
